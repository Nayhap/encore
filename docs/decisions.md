# Design decisions

Code comments refer to these by number, for example `(D6)`.

| # | Decision |
|---|---|
| D1 | **Workspace**: `src-tauri` app crate plus Tauri-independent crates: `crates/encore-core` (domain types, `MusicService` trait, queue), `crates/encore-ytm` (InnerTube client and parsers), `crates/encore-auth` (sessions, cookie import, keychain), `crates/encore-audio` (engine), `crates/encore-lyrics`, `crates/encore-resolver` (stream resolution), plus a `crates/encore-cli` binary for headless and live tests. |
| D2 | **Service abstraction**: `MusicService` trait in `encore-core` with YouTube Music as the only implementation. IDs are `ServiceId + opaque string`. Account context (account key, channel/page id, auth epoch) is immutable per request. A switch cancels in-flight work and old responses are dropped. |
| D3 | **Stream resolution**: Encore's own extractor in Rust (D37), behind the `StreamResolver` trait. Until 0.5 it was a resident yt-dlp helper on the managed Python and Deno of D22; that is gone. Cookies stay in memory and go only to YouTube's API host for the clients that take them, never to googlevideo. No bgutil (GPL-3) and no PO token generator. |
| D4 | **Playability rules**: classify failures as `Challenged / Unavailable / SessionExpired / Network / Unknown`. Do a head+tail range probe before handing the URL to the engine. Keep `range_safe=false` sequential mode when deep ranges fail. Auto-skip with a visible reason, at most 3 consecutive. No silent counterpart substitution: video↔song swap only as an explicit action. One exception is not a substitution: an album's tracks are its songs, so album rows that YouTube lists by their music video resolve to the song (`MPTC<id>` song-credits link of the row, or field 52 of a queue item's `watchEndpoint.params`), and the video is kept as `Track.counterpart` for an explicit "Play the video instead" action. Rows that are videos (video search, video shelves, playlists of videos) stay videos. Playlist edits use the row's own ID (`Entry.video_id`). |
| D5 | **Audio**: `cpal` + `symphonia 0.6` (`isomp4`, `aac`, `mkv`) + `symphonia-adapter-libopus` (register the decoder explicitly) + `rtrb` ring + `rubato` resampler. One actor thread owns state; the realtime callback only drains the ring. Prefer AAC/m4a (itag 141 → 140) when available, Opus/webm otherwise. HTTP range source backed by a disk LRU cache (default 1 GB). Preload the next track 20 s before the end. EOF means decoder done and ring drained. Loudness normalisation from the player response's `loudnessDb`. |
| D6 | **Queue**: owned by Rust (`encore-core`). Entries get UUIDs, and duplicates are allowed. Shuffle-off restores order and keeps history; `next` bypasses repeat-one; `jumpTo`; enumerate partially loaded collections (bounded) before shuffling. Autoplay pulls from the up-next/radio endpoint. Restore state on launch. The queue is saved per account (the account it was restored for, never the one switched to) whole only when it changes; a move to another entry or along the song is a small checkpoint beside it (`queue-at`: the entry, the songs played for radio, the position, and the stamp of the whole write it belongs to), at most every 5 s and on exit, and nothing is written while neither moved. A checkpoint of another whole write is ignored, and a queue saved by 0.6.2 (no stamp) restores as it was. |
| D7 | **Auth, primary**: in-app sign-in through a Tauri `WebviewWindow` with `.incognito(true)` (WebKit's ephemeral store, WebView2's InPrivate). WebKit engines (macOS, WebKitGTK) present a Safari UA; WebView2 keeps its own, which is current Edge's. Read cookies with `cookies_for_url`. The window closes only after the session validates. **Channel/brand picker is an in-app step afterwards** so brand channels can be chosen. |
| D8 | **Auth, browser import**: Edge, then Chrome, Brave, Chromium (Linux), Firefox and Safari (macOS). Selected profile only. Copy the cookie DB with WAL to a temp dir and read it with `rusqlite`; for schema ≥ 24, validate and strip the SHA-256 host prefix. Chromium keys per OS: **macOS** `v10` AES-128-CBC, key from the Safe Storage password via `/usr/bin/security find-generic-password -w` (one "Always Allow" survives app rebuilds), PBKDF2 1003 rounds. **Linux** AES-128-CBC, PBKDF2 1 round: `v10` with the fixed password "peanuts", `v11` with the password from the Secret Service or KWallet. **Windows** `v10` AES-256-GCM with the `Local State` key unwrapped by DPAPI; `v20` (app-bound encryption, current Chrome and Edge) can only be unwrapped by the browser's elevated service, so Encore reports it and points to in-app sign-in, as it does when a running browser keeps the DB locked. Filter exact domains: `.youtube.com`, `music.youtube.com`, `.google.com`. Run `verify_session` rotation immediately after import. Reimplement the readers rather than depending on `rookie`. |
| D9 | **Secrets**: the session (structured cookie jar as JSON, plus account/channel selection) lives in the OS credential store via the `keyring` crate under service `app.encore.desktop`: one Keychain item on macOS, one Secret Service item on Linux. Windows Credential Manager caps a secret at 2,560 bytes, which a session outgrows, so it holds a random 256-bit key instead and the session is sealed with it (AES-256-GCM, the account name as associated data) into `session.enc` in local app data; the file is useless without the credential. No plaintext fallback: without a Secret Service, signing in fails with a message saying so. The Last.fm slot is reserved. Logs redact cookies, tokens, `SAPISID*` and signed URLs; CI includes a canary-secret test. |
| D10 | **InnerTube**: `WEB_REMIX` with the current client version scraped from `music.youtube.com` (fall back to a pinned version). SAPISIDHASH auth (`SAPISID1PHASH`/`3PHASH`) and `X-Goog-AuthUser`/`X-Goog-PageId` for brand channels. Typed renderer parsers with fixture tests, recording real responses to `crates/encore-ytm/fixtures/` with **identifying fields scrubbed**. Continuations are in-memory cursors with a TTL; their pages are read one at a time through the `PlaybackGate` background lane (`encore_core::paging`: after any playback resolve, 1 s after the last background request while someone waits on the list, 2.5 s otherwise), and a list is complete only after the service said it ended (`More::Ended`): a stall, a failure or a limit leaves a partial list that says so. Links that carry `params` (an artist's "All songs") are followed with them (`collection_at`), never rebuilt. Playlist entries are kept separate from tracks (`setVideoId` belongs to the entry). Ambiguous write results return `OutcomeUnknown` and trigger a refetch. |
| D11 | **Storage**: SQLite (`rusqlite`, bundled) in app data, scoped by account. Holds the library/browse cache, play state, settings and the lyrics cache. Nothing secret. Schema 3 adds, in one transactional migration, every table of the D25–D36 wave (`encore_core::local`): durable tables for what the user made or did (play log, bookmarks, saved queues, shuffle cycles, folders, block list, scrobble queue), each row owned by the account key the operation started under (`anonymous` signed out) and never touched by `purge_scope` or sign-out, and per-device caches (Last.fm counts, Wikipedia, audio analysis, album years). Because the file now holds what can't be fetched again, it is backed up whole: `VACUUM INTO` a temporary file, `quick_check`ed, renamed into `backups/` (0600) daily and before every migration, newest three kept. A database found damaged at start (open fails or `quick_check` doesn't pass) is set aside and replaced by the newest backup that opens; only with none is a fresh one started (and D23's sidecars still find the downloads). The user is told which happened. |
| D12 | **Lyrics**: YouTube Music timed lyrics (`ANDROID_MUSIC`/`browse` lyrics tab), then LRCLIB `/api/get` (exact match) and `/api/search` (scored on artist + title + version, duration within ±2 s), then YouTube Music plain lyrics. Output `{ t, text, words? }` plus the source name. Cache positive results for 30 days and negative results for 1 day. Better Lyrics/Unison stay off. |
| D13 | **IPC**: typed commands and events. Try `tauri-specta`/`specta` 2.0 RC pinned exactly; if it doesn't compile cleanly within a short spike, use `ts-rs` plus hand-written invoke wrappers. Events carry revisions (`seekGen`, `trackGen`, `accountGen`). The UI subscribes before fetching the initial snapshot. `player:state` is sent on change; `player:position` is a 2 Hz anchor, also sent immediately on seek or pause, and the UI interpolates ten times a second, and not at all while the window is hidden (D17). Queue changes are splices with a full snapshot on resync. u64 values are strings on the wire. |
| D14 | **Artwork**: an async `art://` custom protocol that takes **opaque art keys**, not URLs. Host allow-list (`*.googleusercontent.com`, `*.ggpht.com`, `i.ytimg.com`), size/MIME limits, and a disk LRU cache. One fetch per key and size runs at a time; a second request waits and reads its file. The dominant hue is computed once per key (a cover with none counts too; one that couldn't be decoded or saved is tried again on its next fetch) after the image is answered, at most two decodes at a time, and returned with track metadata and an event; the UI's `--h`/`--h2` come from it. The same file is used for Now Playing. |
| D15 | **OS integration**: `souvlaki` for the system media controls, media keys, progress and artwork: Now Playing on macOS, the System Media Transport Controls on Windows (bound to the main window's HWND), MPRIS over D-Bus on Linux. macOS holds an App Nap activity while playing and keeps playing when the window is closed (hide instead of quit; the Dock icon brings it back). Windows and Linux have no such way back without a tray icon, so closing quits there, and a second launch focuses the running Encore. |
| D16 | **Licensing**: reimplement and keep Encore MIT. Vendor only permissive code (EJS solver: Unlicense; yt-dlp: Unlicense). Never copy code from GPL-licensed projects. |
| D17 | **Window chrome**: macOS keeps the overlay title bar with native traffic lights. Windows and Linux use an undecorated window with Encore's own minimise, maximise/restore and close buttons at the top right, drawn with theme colours so they read in light and dark; the top bar stays a drag region (double-click maximises). On Windows, resting on maximise opens snap layouts (Win+Z for the focused window), and the window asks DWM for Windows 11's rounded corners. A setting switches to the system title bar for window managers where the custom one misbehaves. Shortcuts show Ctrl off macOS. WebKitGTK paints large blurs on the CPU, so Linux drops the full-screen lyrics' animated blur, the per-line lyric blur, the top bar's backdrop blur and the blurred cover under the side panel's lyrics for plain gradients, tints and solid fills, and shows the playing bars still. Everywhere, the UI writes the interpolated position ten times a second rather than every frame, the seek bar's fill, its playhead and the playing bars move by transform, the time beside the bar is a box of its own size (its text changes lay out only that box), and the lyric fill has no transition, so plain playback never needs a layout of the window or a style pass every frame (without DMA-BUF, WebKitGTK paints every frame on the CPU). The accent's fade to a new song's hues (D14) is written from script over the same 1.2 s and curve, every 33 ms for the first 300 ms (where the curve does most of its change) and every 100 ms after, about 20 restyles instead of 72, since a CSS transition of `--h` restyles the whole document every frame; reduced motion and a hidden window jump. A hidden window keeps the position anchors but writes no position, and catches up once when shown; the sleep timer's one-second clock runs only while a timed sleep shows. The AppImage carries Ubuntu 22.04's WebKitGTK on the host's newer Mesa, where WebKit's DMA-BUF renderer can abort the web process (seen on Fedora 44, Mesa 26). Turning that renderer off (`WEBKIT_DISABLE_DMABUF_RENDERER=1`) also turns off accelerated compositing on WebKitGTK 2.44 and later, so the AppImage instead sets `WEBKIT_DMABUF_RENDERER_FORCE_SHM=1` at start: GPU compositing stays, and frames reach the window through shared memory, never importing a DMA-BUF into the host's Mesa. If the web process still crashes in that mode, Encore writes `webkit-software` (its version) in the data folder and restarts through the normal exit; with that marker the AppImage sets `WEBKIT_DISABLE_DMABUF_RENDERER=1` until Encore's version changes. Either variable set by the user wins, and the log says which mode runs. Any other web process crash reloads the page, at most twice per launch, rather than leaving a blank window. The Linux CSS reductions above stay until GPU compositing is confirmed on Linux hosts. |
| D18 | **History reporting**: plays go to YouTube Music history through Encore's own signed-in `WEB_REMIX` `/player` call, used only for `playbackTracking` (never yt-dlp's `--mark-watched`, which reports resolves and preloads under another client). The account and channel are snapshotted when the play starts; the `/player` call and every ping use that snapshot (brand `X-Goog-PageId`, the `_u` SAPISIDHASH, `X-Goog-AuthUser` from the session), and a switch drops the rest of the play's pings. One `playback` ping after 2 s of audible playback, then `watchtime` pings with the stretches actually heard on the response's flush schedule (default 10, 20, 30 s, then every 40 s), on pause, and a last one with `final=1`. One `cpn` per play. Stats URLs must be https `s.youtube.com`/`www.youtube.com`/`music.youtube.com` under `/api/stats/`, no redirects are followed, and they are redacted from logs. Settings → Playback → "Send plays to YouTube history" (on by default; signed-in only). YouTube's own pause is shown from the History page, with a link to My Activity. |
| D19 | **History page**: a sidebar item under Library. `FEmusic_history` day groups in YouTube's order; each row is the version that was played. "Remove from history" sends the row's `REMOVE_FROM_HISTORY` `feedbackToken` to `feedback` and is done only when every response says `isProcessed`. Tokens stay in Rust behind opaque row ids bound to the account epoch; history rows are never cached on disk. |
| D20 | **Playlist management**: `playlist/create` (seeded with `videoIds`, so "New playlist…" from "Add to playlist" is one write; private by default), `browse/edit_playlist` for name, description, privacy and `ACTION_MOVE_VIDEO_BEFORE`, `playlist/delete`. Adds use `DEDUPE_OPTION_CHECK`; the duplicate dialog in the answer becomes `MutationOutcome::Duplicate` and the UI asks before retrying with `DEDUPE_OPTION_SKIP`. Editability and privacy come from the editable header. Optimistic UI reverts on `Rejected` and refetches on `OutcomeUnknown`; a create, add or move with an unknown outcome is never retried automatically. Every write drops the cached copies and emits one event so the sidebar, Library, the open playlist and "Add to playlist" update together. |
| D21 | **Song/Video switch**: a track-menu action and a Song \| Video control in the now playing header, shown when a pair exists. The pair comes from `Track.counterpart`, then the `next` wrapper (either side, with its `segmentMap`), then a search accepted only on the same title, first artist and a length within 5 s. Switching replaces the queue entry's track in place (same uid, place and source), maps the position through the segment map when inside a shared segment and otherwise restarts at 0, and keeps a paused entry paused. Like, history and lyrics follow the version that is playing. Audio only. |
| D22 | **Managed player components** (retired in 0.6, replaced by D37). Encore 0.3 to 0.5 downloaded a pinned CPython, Deno and the yt-dlp wheels into `<app data>/runtimes/` after the user approved, behind a setup sheet. The native resolver needs none of it: from 0.6 there is no setup sheet, no download and no `SetupNeeded` failure, and `encore_resolver::cleanup` removes 0.5's `runtimes/`, the `venv/` and helper of the older `resolver/`, `<cache>/yt-dlp/` and `<cache>/deno/` once, under 0.5's own install lock (opened as 0.5 opens it, created if missing, held until done is recorded, never deleted; nothing is deleted without it), deleting only the names 0.5 made (component folders by their `<slug>-<version>-<fingerprint>` id), never through a symlink or junction, and leaving the job for the next launch while a file is in use. Done is recorded as `<app data>/runtimes.removed`. |
| D23 | **Downloads and offline**: downloads are a personal offline cache inside Encore, not an export: the raw audio YouTube serves (AAC/m4a or Opus/webm, the D5 order, no transcoding, no tags), named by id under `<app data>/downloads/audio/<videoId>-<itag>.<ext>` (0600, folder 0700), never in a temporary folder; no "Show in Finder", no export, no movable folder. Songs are per device and stored once; pins and kept collections (playlists, albums, liked songs) are per account (`RequestContext.account`), each collection an ordered snapshot. A song stays while any pin or member wants it; removing a song removes the account's own pin, so another account's download or a kept collection keeps it, and says so. Sign-out never deletes downloads; another account's collections stop syncing and say so. The index is in SQLite (schema 2, a real migration). Each file's JSON sidecar is written inside its install, before the song counts as ready; if `Store::open` sets a damaged database aside, the songs are found again from their sidecars and the user is told, but kept collections have to be downloaded again. One worker, holding a lock file so the app and `encore-cli` never fetch at once (the CLI's pause flag reaches the app's worker through the store): the resolver only resolves (D3, D37), Rust fetches 1 MiB ranges with `Accept-Encoding: identity`, streams each body to disk no longer than asked for, checks every 206's Content-Range and length, starts over on a 200 at an offset, once on 416, and times out a stall rather than a slow link. A partial file is continued only for the same itag and length when its last 4 KiB still match. A file counts once it decodes (first packets) and is hashed; it is installed only while its attempt number is current and something still wants it, inside a transaction, so cancel and removal always win; files are deleted only inside a transaction that still finds the song being removed, so an old removal never touches a new download. Background requests are admitted only while no playback resolve runs (`PlaybackGate`), one at a time, 2–4 s apart; the resolver no longer repeats a bot check, and a refused fresh URL is resolved once more, then is a failure of that song. Only the extractor's bot check pauses downloads: 10 minutes, then 30, then stopped until the user retries. Disk full, offline and a folder that can't be locked are waits of their own, apart from the user's pause. Collection checks go through one queue, bound to the account and session that asked: on keep, at launch and account change and on reconnect (lists checked in the last 15 minutes are skipped), after Encore's own playlist and like changes (asked again while one runs, it runs once more), on request, otherwise every 6 h, and a failed check, or one that never read the whole list, again after 30 minutes; pages are read about 2.5 s apart. Only a check without an error counts as up to date, and removals apply only after a list that really ended (`More::Ended`); a list that suddenly reads as empty is a failed check, and a greyed-out row keeps its song if it is already downloaded (nothing new is fetched for it). Album rows download the song (D4). Offline: a failed request plus a probe; the player plays files first, passes over songs that aren't downloaded (not counted as D4 skips) in every step and when the connection drops, drops preloads that stream, keeps repeat-one, stops with one message when nothing is left; radio, likes, edits, version switch and search are refused with a reason. History pings belong to the connection a play started on: offline nothing is opened or sent, and a play that lost its connection is never reported, even after it comes back. Lyrics are kept with a download (a miss is asked again after a week, a failed lookup not remembered); the 544 px cover is kept, answers every size offline, and its address never expires. Loudness comes from `/player` for every download, copied or fetched. |
| D24 | **In-app updates**: `tauri-plugin-updater` 2.14, driven from Rust only (no JS API, no updater permission), against `latest.json` on the latest published GitHub release (`releases/latest/download/`), so drafts and pre-releases are never offered and publishing a draft ships it. Every package carries the Tauri CLI's minisign signature, checked against the public key in `tauri.conf.json` with `requireSignedVersion`; no downgrades. `release.yml` builds the packages (macOS `app,dmg`, its universal `.app.tar.gz` listed for both Mac architectures; NSIS and MSI each update their own install; AppImage) with the key on the build step only, and `scripts/release-manifest.sh` writes the manifest from the uploaded files and fails unless all five entries are there once, the tag matches every version and each signature verifies. `tauri.conf.json` leaves the packages off, so other builds need no key. Checks 20 s after launch, every 6 h, on reconnect when the last answer is over 6 h old (coalesced within 15 min) and on request; background checks wait while offline, a manual one always tries, and GitHub failures never touch the connection state (D23) or download backoff; failures back off 30 min, 2 h, 6 h. Automatic (default): downloaded in the background (stopped over 300 MB or after a 60 s stall), staged as `<cache>/updates/<version>.<ext>` with its raw manifest, by temp file and rename, one version at most, rebuilt with `restore_update` and verified again at launch, deleted once that version runs. Off: still checks and says once per version that one is out, downloads only when asked. Installs only on **Restart to update** (pauses, then relaunches into the new version where it was) or when Encore quits with one ready (macOS `RunEvent::Exit`; Windows and Linux hold `CloseRequested` and say "Installing the update…"); never by itself. Turning automatic off disarms install-at-quit for what it downloaded. Skip per version (automatic checks ignore it, a manual one shows it). One exit: the first quit, close or Restart to update runs it and every other exit request waits for it (a quit during Restart to update waits for the install). Before any install or exit, `Core::prepare_exit`: playback stopped (paused, nothing loading starts, no command starts it) and the queue saved now (an A–B loop ends, giving back repeat-one, and a sleep timer is cancelled, D26), the last history ping and the local play log's open play closed with the time heard (≤ 2 s, D30), downloads quiesced for the session (not the user's pause), the resolver closed, a running challenge solve interrupted (D37). A package handed to an installer (a `.handed` marker) that is still there at the next launch didn't install (a declined Windows prompt): it waits for Restart to update rather than starting the installer at every quit. Downloads have no total time limit, only the stall limit. Install kinds from `bundle_type()`: macOS refuses a translocated copy, the disk image or a bundle or folder Encore can't create and rename in (probed for real, so privacy controls count), checked again before installing, which keeps the plugin's administrator-password fallback from ever being reached; development builds never check; a `.deb` is never installed, it links to the release. Operation generations and the status revision keep late results from overwriting newer state (D13). A test endpoint can be set in `<data>/update-endpoint` (https only, logged). |
| D25 | **Bookmarks**: local, durable, per owner (`bookmarks`, D11; signed out is the `anonymous` owner), never synced. Three kinds: a page (`PageRef`: a collection with its `params`, an artist, a browse page; never a cursor), a song (the `Track`, `liked` cleared), a moment (a song and whole seconds into it). The same page or song twice, or a moment within 2 s of one kept, returns the bookmark already there. Made from the track menu "Bookmark", a playlist's, album's or artist's menu "Bookmark", the player bar ⋯ "Bookmark this moment", <kbd>B</kbd>, and the palette ("Bookmark this page", "Bookmark this moment"); the same item reads "Remove bookmark" once kept. Listed in Library → **Bookmarks** (Moments, Songs, Pages; newest first; a moment shows its time and where it falls in the song). Opening: a page navigates; a song plays as songs do elsewhere (with its radio online, alone offline); a moment does the same and seeks once that song is playing, or just seeks when it is the song playing now. Offline, a song that isn't downloaded is dimmed and says why. |
| D26 | **A–B loop and sleep timer**: both are Rust's, transient (never saved, never a setting) and shown in the snapshot (`loop`, `sleep`). **Loop**: track menu "Loop a part…" (a 15 s loop from the playhead, adjusted by dragging), <kbd>A</kbd> (start, end, clear), Shift-drag on the seek bar; the bar shows a lit band with draggable, keyboard-adjustable ends and a pill with the times and ✕. It needs the song loaded, a seekable stream and a known length; at least 1 s. The decoder enforces it: audio pushed into the ring stops at B's frame and goes on with A's, so the wrap is exact to the frame and gapless (the only seams are the AAC/Opus decoder reset at A). Positions follow a timeline of marks (frame → song time) kept per ring. A loop set after the decoder passed B continues in a spare ring the callback switches to at B's frame; when the switch message arrives late, B overruns by at most one output buffer plus the actor's 15 ms turn (the counter is then reset to B, so positions stay right). Seeking back from the end of a file reopens the source (neither demuxer seeks from EOF). While a loop runs: nothing is preloaded, the engine never promotes a next deck (the song never ends), repeat-one is set aside and restored, and wraps are not new plays. Seeking outside the loop, a song change or a version switch ends it. **Sleep timer**: player bar moon button (a chip with the time left while one runs) and the palette: 15, 30, 45 min, 1 h, end of this song, end of the queue, off. A timed sleep fades over its last 10 s in the engine (a gain on top of the volume, squared curve; the saved volume is untouched), then pauses; resuming plays at full volume; a timer that runs out while paused just ends. End of song and end of queue set the engine's `hold_next`, so the callback never takes up a preloaded deck: the next song then waits paused at 0:00. End of queue adds no radio meanwhile and stops at the last entry even under repeat-all. End of song is refused while a loop runs ("Clear the loop to stop at the end of this song"). |
| D27 | **Cover ambience and Hide podcasts**: **Ambience**: the playing song's cover, drawn small (120 px `art://`, or the mock motif) and blurred (44 px in the now playing panel, 90 px under full-screen lyrics) with raised saturation, behind the now playing panel (masked away before the queue) and full-screen lyrics only, never behind lists or tables. Strength `--wash-alpha` per theme (0.5 dark, 0.42 light; ×0.55 under lyrics so text keeps its contrast). Settings → Appearance → "Cover ambience", on by default, sits under and needs "Colour from artwork". Covers crossfade (900 ms) between songs; reduced motion drops the crossfade and the lyrics' drifting blobs. Linux keeps D17's gradients: no wash and no setting. No new network request (the cover is already cached). **Hide podcasts**: one setting in Appearance (off by default, kept in `settings`). One predicate over `TrackKind::Episode`, the only podcast content that reaches Encore (show cards are dropped at parse), applied after the cache: `features::taste::filter_page` filters Home, Explore, browse pages and more shelves on the way out and drops shelves left empty, so flipping it is instant and the cached page stays whole; the player's `Admission` (D36) refuses episodes for radio, Autoplay and the other admission paths while it's on. Views already holding a page filter it the same way in the UI. |
| D28 | **Song details, tempo and key**: track menu (and palette) "Song details": a sheet with tempo and key, album and its year (from the album, through `collection`), length, plays (this account's counted plays in the play log, Last.fm's count when connected, YouTube's play count), and the file Encore has (downloaded or cached, format, bitrate, size). Tempo and key are estimated only when asked ("Estimate"), only from a file Encore already has (the download, else a complete audio-cache file); nothing is fetched and playback is never tapped. `encore-analysis` (original DSP on Symphonia and rustfft): mono at about 11 kHz, at most 10 minutes; tempo from a spectral-flux onset envelope's autocorrelation in 60–200 BPM with a log-normal prior at 120 BPM and sub-frame refinement; key from a whole-song chroma (55 Hz–1.76 kHz, frames normalised) against the Krumhansl–Kessler profiles. Each has a confidence; below 0.25 (tempo) or 0.6 (key) it shows "—". About 0.2 s a song on an M4. One estimate at a time, cancellable. Results in `audio_analysis` with the file (`<itag>:<bytes>`) and estimator version: another file or version can be estimated again. Always labelled "Estimated by Encore from the audio". |
| D29 | **Wikipedia on artist pages**: only when YouTube gives the artist no description. Wikipedia's REST `page/summary` (English, the language Encore asks YouTube in), trying the name, then "Name (band)", "(musician)", "(singer)"; a page counts only if it is an article (not disambiguation), its title is that name or variant (case and accents aside) and its short description names a musician or band (a strong word such as band, singer, rapper, duo, or a weak one such as group, producer, artist together with a music word).
