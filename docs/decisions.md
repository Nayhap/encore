# Design decisions

Code comments refer to these by number, for example `(D6)`.

| # | Decision |
|---|---|
| D1 | **Workspace**: `src-tauri` app crate plus Tauri-independent crates: `crates/encore-core` (domain types, `MusicService` trait, queue), `crates/encore-ytm` (InnerTube client and parsers), `crates/encore-auth` (sessions, cookie import, keychain), `crates/encore-audio` (engine), `crates/encore-lyrics`, `crates/encore-resolver` (stream resolution), plus a `crates/encore-cli` binary for headless and live tests. |
| D2 | **Service abstraction**: `MusicService` trait in `encore-core` with YouTube Music as the only implementation. IDs are `ServiceId + opaque string`. Account context (account key, channel/page id, auth epoch) is immutable per request. A switch cancels in-flight work and old responses are dropped. |
| D3 | **Stream resolution**: a resident **yt-dlp helper** (Python, pinned `yt-dlp` + `yt-dlp-ejs`, on the managed components of D22). JSON lines over stdin/stdout. Cookies are passed **in memory per request** through `YoutubeDL`'s cookie jar and never written to disk. JS runtime: the managed Deno (D22), passed via `--js-runtimes`. No bgutil (GPL-3). A `StreamResolver` trait keeps the native resolver as a later, swappable implementation. |
| D4 | **Playability rules**: classify failures as `Challenged / Unavailable / SessionExpired / Network / Unknown`. Do a head+tail range probe before handing the URL to the engine. Keep `range_safe=false` sequential mode when deep ranges fail. Auto-skip with a visible reason, at most 3 consecutive. No silent counterpart substitution: video↔song swap only as an explicit action. One exception is not a substitution: an album's tracks are its songs, so album rows that YouTube lists by their music video resolve to the song (`MPTC<id>` song-credits link of the row, or field 52 of a queue item's `watchEndpoint.params`), and the video is kept as `Track.counterpart` for an explicit "Play the video instead" action. Rows that are videos (video search, video shelves, playlists of videos) stay videos. Playlist edits use the row's own ID (`Entry.video_id`). |
| D5 | **Audio**: `cpal` + `symphonia 0.6` (`isomp4`, `aac`, `mkv`) + `symphonia-adapter-libopus` (register the decoder explicitly) + `rtrb` ring + `rubato` resampler. One actor thread owns state; the realtime callback only drains the ring. Prefer AAC/m4a (itag 141 → 140) when available, Opus/webm otherwise. HTTP range source backed by a disk LRU cache (default 1 GB). Preload the next track 20 s before the end. EOF means decoder done and ring drained. Loudness normalisation from the player response's `loudnessDb`. |
| D6 | **Queue**: owned by Rust (`encore-core`). Entries get UUIDs, and duplicates are allowed. Shuffle-off restores order and keeps history; `next` bypasses repeat-one; `jumpTo`; enumerate partially loaded collections (bounded) before shuffling. Autoplay pulls from the up-next/radio endpoint. Restore state on launch. |
| D7 | **Auth, primary**: in-app sign-in through a Tauri `WebviewWindow` with `.incognito(true)` (WebKit's ephemeral store, WebView2's InPrivate). WebKit engines (macOS, WebKitGTK) present a Safari UA; WebView2 keeps its own, which is current Edge's. Read cookies with `cookies_for_url`. The window closes only after the session validates. **Channel/brand picker is an in-app step afterwards** so brand channels can be chosen. |
| D8 | **Auth, browser import**: Edge, then Chrome, Brave, Chromium (Linux), Firefox and Safari (macOS). Selected profile only. Copy the cookie DB with WAL to a temp dir and read it with `rusqlite`; for schema ≥ 24, validate and strip the SHA-256 host prefix. Chromium keys per OS: **macOS** `v10` AES-128-CBC, key from the Safe Storage password via `/usr/bin/security find-generic-password -w` (one "Always Allow" survives app rebuilds), PBKDF2 1003 rounds. **Linux** AES-128-CBC, PBKDF2 1 round: `v10` with the fixed password "peanuts", `v11` with the password from the Secret Service or KWallet. **Windows** `v10` AES-256-GCM with the `Local State` key unwrapped by DPAPI; `v20` (app-bound encryption, current Chrome and Edge) can only be unwrapped by the browser's elevated service, so Encore reports it and points to in-app sign-in, as it does when a running browser keeps the DB locked. Filter exact domains: `.youtube.com`, `music.youtube.com`, `.google.com`. Run `verify_session` rotation immediately after import. Reimplement the readers rather than depending on `rookie`. |
| D9 | **Secrets**: the session (structured cookie jar as JSON, plus account/channel selection) lives in the OS credential store via the `keyring` crate under service `app.encore.desktop`: one Keychain item on macOS, one Secret Service item on Linux. Windows Credential Manager caps a secret at 2,560 bytes, which a session outgrows, so it holds a random 256-bit key instead and the session is sealed with it (AES-256-GCM, the account name as associated data) into `session.enc` in local app data; the file is useless without the credential. No plaintext fallback: without a Secret Service, signing in fails with a message saying so. The Last.fm slot is reserved. Logs redact cookies, tokens, `SAPISID*` and signed URLs; CI includes a canary-secret test. |
| D10 | **InnerTube**: `WEB_REMIX` with the current client version scraped from `music.youtube.com` (fall back to a pinned version). SAPISIDHASH auth (`SAPISID1PHASH`/`3PHASH`) and `X-Goog-AuthUser`/`X-Goog-PageId` for brand channels. Typed renderer parsers with fixture tests, recording real responses to `crates/encore-ytm/fixtures/` with **identifying fields scrubbed**. Continuations are in-memory cursors with a TTL. Playlist entries are kept separate from tracks (`setVideoId` belongs to the entry). Ambiguous write results return `OutcomeUnknown` and trigger a refetch. |
| D11 | **Storage**: SQLite (`rusqlite`, bundled) in app data, scoped by account. Holds the library/browse cache, play state, settings and the lyrics cache. Nothing secret. |
| D12 | **Lyrics**: YouTube Music timed lyrics (`ANDROID_MUSIC`/`browse` lyrics tab), then LRCLIB `/api/get` (exact match) and `/api/search` (scored on artist + title + version, duration within ±2 s), then YouTube Music plain lyrics. Output `{ t, text, words? }` plus the source name. Cache positive results for 30 days and negative results for 1 day. Better Lyrics/Unison stay off. |
| D13 | **IPC**: typed commands and events. Try `tauri-specta`/`specta` 2.0 RC pinned exactly; if it doesn't compile cleanly within a short spike, use `ts-rs` plus hand-written invoke wrappers. Events carry revisions (`seekGen`, `trackGen`, `accountGen`). The UI subscribes before fetching the initial snapshot. `player:state` is sent on change; `player:position` is a 2 Hz anchor, also sent immediately on seek or pause, and the UI interpolates with rAF. Queue changes are splices with a full snapshot on resync. u64 values are strings on the wire. |
| D14 | **Artwork**: an async `art://` custom protocol that takes **opaque art keys**, not URLs. Host allow-list (`*.googleusercontent.com`, `*.ggpht.com`, `i.ytimg.com`), size/MIME limits, and a disk LRU cache. The dominant hue is computed once and returned with track metadata; the UI's `--h`/`--h2` come from it. The same file is used for Now Playing. |
| D15 | **OS integration**: `souvlaki` for the system media controls, media keys, progress and artwork: Now Playing on macOS, the System Media Transport Controls on Windows (bound to the main window's HWND), MPRIS over D-Bus on Linux. macOS holds an App Nap activity while playing and keeps playing when the window is closed (hide instead of quit; the Dock icon brings it back). Windows and Linux have no such way back without a tray icon, so closing quits there, and a second launch focuses the running Encore. |
| D16 | **Licensing**: reimplement and keep Encore MIT. Vendor only permissive code (EJS solver: Unlicense; yt-dlp: Unlicense). Never copy code from GPL-licensed projects. |
| D17 | **Window chrome**: macOS keeps the overlay title bar with native traffic lights. Windows and Linux use an undecorated window with Encore's own minimise, maximise/restore and close buttons at the top right, drawn with theme colours so they read in light and dark; the top bar stays a drag region (double-click maximises). On Windows, resting on maximise opens snap layouts (Win+Z for the focused window), and the window asks DWM for Windows 11's rounded corners. A setting switches to the system title bar for window managers where the custom one misbehaves. Shortcuts show Ctrl off macOS. WebKitGTK paints large blurs on the CPU, so Linux drops the full-screen lyrics' animated blur, the per-line lyric blur and the top bar's backdrop blur for plain gradients and solid fills. |
| D18 | **History reporting**: plays go to YouTube Music history through Encore's own signed-in `WEB_REMIX` `/player` call, used only for `playbackTracking` (never yt-dlp's `--mark-watched`, which reports resolves and preloads under another client). The account and channel are snapshotted when the play starts; the `/player` call and every ping use that snapshot (brand `X-Goog-PageId`, the `_u` SAPISIDHASH, `X-Goog-AuthUser` from the session), and a switch drops the rest of the play's pings. One `playback` ping after 2 s of audible playback, then `watchtime` pings with the stretches actually heard on the response's flush schedule (default 10, 20, 30 s, then every 40 s), on pause, and a last one with `final=1`. One `cpn` per play. Stats URLs must be https `s.youtube.com`/`www.youtube.com`/`music.youtube.com` under `/api/stats/`, no redirects are followed, and they are redacted from logs. Settings → Playback → "Send plays to YouTube history" (on by default; signed-in only). YouTube's own pause is shown from the History page, with a link to My Activity. |
| D19 | **History page**: a sidebar item under Library. `FEmusic_history` day groups in YouTube's order; each row is the version that was played. "Remove from history" sends the row's `REMOVE_FROM_HISTORY` `feedbackToken` to `feedback` and is done only when every response says `isProcessed`. Tokens stay in Rust behind opaque row ids bound to the account epoch; history rows are never cached on disk. |
| D20 | **Playlist management**: `playlist/create` (seeded with `videoIds`, so "New playlist…" from "Add to playlist" is one write; private by default), `browse/edit_playlist` for name, description, privacy and `ACTION_MOVE_VIDEO_BEFORE`, `playlist/delete`. Adds use `DEDUPE_OPTION_CHECK`; the duplicate dialog in the answer becomes `MutationOutcome::Duplicate` and the UI asks before retrying with `DEDUPE_OPTION_SKIP`. Editability and privacy come from the editable header. Optimistic UI reverts on `Rejected` and refetches on `OutcomeUnknown`; a create, add or move with an unknown outcome is never retried automatically. Every write drops the cached copies and emits one event so the sidebar, Library, the open playlist and "Add to playlist" update together. |
| D21 | **Song/Video switch**: a track-menu action and a Song \| Video control in the now playing header, shown when a pair exists. The pair comes from `Track.counterpart`, then the `next` wrapper (either side, with its `segmentMap`), then a search accepted only on the same title, first artist and a length within 5 s. Switching replaces the queue entry's track in place (same uid, place and source), maps the position through the segment map when inside a shared segment and otherwise restarts at 0, and keeps a paused entry paused. Like, history and lyrics follow the version that is playing. Audio only. |
| D22 | **Managed player components**: Encore never uses a system Python or JS runtime. With the user's approval (a setup sheet on first launch, and again whenever play is pressed without them), it downloads pinned, relocatable builds into `<app data>/runtimes/`: CPython from astral-sh/python-build-standalone (`install_only_stripped`), Deno (one binary; yt-dlp's recommended runtime), and the pure-Python wheels of yt-dlp, yt-dlp-ejs and certifi unpacked straight into an import folder (no pip, no venv, no network from Python). Why always managed: the system interpreters were the source of every setup failure so far (missing Python on macOS and Windows, Debian's split `python3-venv`, the AppImage environment leaking into the system Python), and a fixed set is the one CI and users actually test. Cost (MiB): macOS arm64 64 to download, 121 on disk (Python 31, Deno 78, yt-dlp 16); Linux x64 77 to download, about 156 on disk (Python 48, Deno 92, yt-dlp 16); Windows x64 65 to download, 141 on disk (Python 34, Deno 94, yt-dlp 13). Python is trimmed of IDLE, Tk, pip, headers, tests and the embedding library (its executable is static on macOS and Linux), roughly halving it. Versions, official HTTPS URLs, sizes and SHA-256 checksums are pinned in `encore-resolver/src/runtimes/manifest.rs`; each download is size-checked while streaming and hashed from disk before use. Archives unpack into a fresh staging folder with path checks (relative, no `..`, links may only point down, no devices), executable bits kept, macOS quarantine cleared, then each component is renamed into place with a `.encore-ready` marker holding its fingerprint, and the set is run once (Python imports yt-dlp, `deno --version`) before `active.json` names it, written by temp file and rename. A cross-process lock file serialises installs between Encore windows; partial downloads and staging are discarded on the next run, verified downloads reused. A newer Encore with newer pins updates on launch without asking again (the setup copy says so), keeping the old set in use until the new one is ready. Settings → Playback shows the components, with Reinstall and Remove. Without the components resolving fails as `SetupNeeded`: the song is kept paused (not skipped) and starts once setup ends. |
| D23 | **Downloads and offline**: downloads are a personal offline cache inside Encore, not an export: the raw audio YouTube serves (AAC/m4a or Opus/webm, the D5 order, no transcoding, no tags), named by id under `<app data>/downloads/audio/<videoId>-<itag>.<ext>` (0600, folder 0700), never in a temporary folder; no "Show in Finder", no export, no movable folder. Songs are per device and stored once; pins and kept collections (playlists, albums, liked songs) are per account (`RequestContext.account`), each collection an ordered snapshot. A song stays while any pin or member wants it. Sign-out never deletes downloads; another account's collections stop syncing and say so. The index is in SQLite (schema 2, a real migration); a JSON sidecar next to each file rebuilds it if `Store::open` set a damaged database aside. One worker, holding a lock file so the app and `encore-cli` never fetch at once: the yt-dlp helper only resolves (D3), Rust fetches 1 MiB ranges with `Accept-Encoding: identity`, checks every 206's Content-Range and length, restarts on a 200 at an offset, starts over once on 416. A partial file is continued only for the same itag and length when its last 4 KiB still match. A file counts once it decodes (first packets) and is hashed; it is installed only while its attempt number is current and something still wants it, inside a transaction, so cancel and removal always win. Resolves wait for playback's (`PlaybackGate`) and are 2–4 s apart; the resolver no longer repeats a bot check, and a refused fresh URL is resolved once more, then is a failure of that song. Only the extractor's bot check pauses downloads: 10 minutes, then 30, then stopped until the user retries. Disk full, offline and setup needed are waits of their own, apart from the user's pause. Collections are checked on keep, at launch, on reconnect, after Encore's own playlist and like changes, on request, and otherwise every 6 h; removals apply only after a list that really ended (`More::Ended`). Album rows download the song (D4). Offline: a failed request plus a probe; the player plays files first, passes over songs that aren't downloaded (not counted as D4 skips), keeps repeat-one, stops with one message when nothing is left; radio, likes, edits, version switch and search are refused with a reason; history pings are not opened or sent offline and an offline play is never reported later. Lyrics are kept with a download (a miss is asked again after a week, a failed lookup not remembered); the 544 px cover is kept and answers every size offline. Loudness comes from `/player` for normalisation. Removing the player components leaves downloads playable. |
